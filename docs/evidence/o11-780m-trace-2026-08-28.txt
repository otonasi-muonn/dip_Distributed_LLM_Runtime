What this establishes:

  - The stall is inside the encode loop, not in GPU completion. The last event
    is an encode, and `wait(final)` is never reached.
  - The GPU work that was submitted did complete: both wait(partial) calls
    returned with retries=0.
  - There are no WaitAny lines at all, so the "WaitAny retries forever on

    kernels, so the stall is somewhere in nodes 129..192 of 1591. `submit #2`
    never appears.

Confirmed stable: the trace was still exactly these 10 lines at 678 s after the
generation started (well past the 300 s cutoff). The encode loop is not slow,
it has stopped.

### The one FAIL

  GATED_DELTA_NET(name=__fgdn_ch__-0, type=f32, ne=[4096,640,1,1],
    sources=f32[128,16,512,1], f32[128,16,512,1], f32[128,32,512,1],
            f32[1,32,512,1], f32[1,32,512,1], f32[128,128,32,1]): FAIL
  [GATED_DELTA_NET] inf mismatch: WebGPU=-inf  CPU=-2.914e37

The chunked Gated DeltaNet at batch 512. The autoregressive form
(__fgdn_ar__, batch 1) passed.

⚠️ Do not read this as a confirmed kernel defect yet. test-backend-ops drives ops
with random inputs, and the CPU reference here produced -2.9e37, itself within a
factor of ~10 of the f32 maximum. Both sides are near overflow, so this may be an
unstable op fed values a real model would never produce. What is established is
that the two backends disagree at this shape; whether that matters for real
activations is not.

### The four NOT SUPPORTED

  2x MUL_MAT_ID ffn_moe_gate_up-0, src0=F32[2048,1024,256] = 2,147,483,648 bytes
      maxStorageBufferBindingSize here is 2,147,483,644 - over by exactly 4
      bytes, so supports_op rejects it on size (F12). src0 is F32 only because
      the fused gate_up tensor is built at load time rather than read from the
      file, so under no_alloc it keeps the default type. The real weights are
      Q2_K/Q3_K, roughly 8x smaller. This is an artifact of how the ops were
      exported, not a property of the model.

  2x FLASH_ATTN_EXT __fattn__-3
      ggml-webgpu compiles flash attention out under Emscripten. The Runtime
      also disables flash attention at run time (a fork commit in llmlet's
      main.cpp, "disable flash_attn to make it compatible with the rpc
      backend"), so these ops do not appear in the graph the peer actually
      receives. The exporter builds with default params, which is why they are
      in the file at all.

### A slow case, not a stalled one

This one took over 12 minutes while its neighbours took seconds; the same gather

### What the verdict caught that nothing else would have

Run through the pattern the judge used before this run, anchored to the two
leading spaces of a case line:

  observed 135, OK 131, FAIL 0, NOT SUPPORTED 4

The FAIL is invisible there, because test-backend-ops prints the mismatch report
inline ahead of the case, so that line does not start with two spaces. The only
signal was that 135 did not equal the 136 cases in the input file. With the
pattern no longer anchored:

  observed 136, OK 131, FAIL 1, NOT SUPPORTED 4     (131 + 1 + 4 = 136)

Counting what should have run, and not only what printed, is what made a real
failure visible.
