# Qwen3.6 Runtime Compatibility Result (2026-08-28)

対象: `Qwen3.6-35B-A3B` text-only GGUF を、pin 済み llmlet / `ktock/llama.cpp` fork +
WebGPU + llama.cpp RPC のブラウザ分散 Runtime で動かせるか。

作業ブランチ: `feat/qwen36-moe-compat` (base = `origin/main` = `e739d7a`)

⚠️ **測定環境について先に断る。** 本作業の実測はすべて開発機 1 台で行った。この機は
**AMD Radeon 780M (RDNA-3 統合GPU、専用VRAM 0.5GB / システムRAM 31.29GB)** で、
discrete GPU を持たない。`CONSTRAINTS.md` F12 / F20 の既存数値は NVIDIA Turing のもので、
**別の機体**である。したがって **GPU 性能・GPU メモリに関する結果は、実際の peer 機
(VRAM 8GB 以上) で取り直すまで製品判断の根拠にしてはいけない。**

---

## 1. 結論

**PARTIALLY SUPPORTED.**

- **Qwen3.6 の architecture / tokenizer / tensor 構造は、pin 済み Runtime がそのまま扱える。**
  静的解析と機械的な突き合わせで確定 (Gate 1)。追加実装は不要だった。
- **Gated DeltaNet / hybrid recurrent / IMRoPE / gated attention は、パッチ無しの
  現行 Runtime で既に動く。** 実ブラウザ・実 WebGPU peer・実生成で確認 (L1)。
- **MoE に唯一足りなかった `GGML_OP_MUL_MAT_ID` を backport し、数値の正しさまで検証した**
  (`patches/0004` / Gate 4)。`test-backend-ops` で **WebGPU 455/455 pass**。
- **しかし、実 MoE モデルの生成は WebGPU peer 上で完走しなかった。** 同じモデルが CPU peer
  では 30 秒未満で完答するので、**問題領域を「WebGPU backend 固有、または WebGPU backend と
  実 MoE graph / RPC の組み合わせ」まで絞れた** (O11)。⚠️ **hang / 極端な同期遅延 /
  特定 op・graph 構成のどれかは未確定。**
- したがって **Qwen3.6 実モデルの load / prefill / decode / 分散生成 (Gate 6C 以降) には
  到達していない。**

つまり **「Qwen3.6 対応に必要だった既知の静的 blocker はほぼ解消した。ただし real MoE graph を
WebGPU peer で最後まで実行できることは、まだ証明できていない」**。

## 5. 残 blocker

### O11 — MoE グラフが WebGPU peer で返らない

**最後に到達した地点**: peer は RPC コマンドを 14 件処理した時点で 1 つの `graph_compute`
の中に入り、返らない。エラーは **requester 側にも peer 側にも一切出ない**。

観測されている事実だけを並べる:

| 観測 | 値 |
|---|---|
| 同じモデル・同じ patch・**CPU peer** | 30 秒未満で `Paris` |
| 同じ peer・**dense モデル** (Qwen3.5-0.8B / Qwen2.5-0.5B) | 数十秒で `Paris` |
| `MUL_MAT_ID` の数値 | WebGPU で 455/455 一致 |
| `MUL_MAT_ID` 単体性能 (128 experts, k=2048, n=1) | 3398-5056 us/run、4.98-7.41 GFLOPS |
| MoE 実行中の GPU 利用率 | **5.8%** (単一 3D エンジン)。⚠️ この値からは何も断定できない — **同期ボトルネックでも普通に出る**し、GPU が動いていることは **graph が前進している証明にもならない** (同じ箇所を繰り返していても観測される) |
| peer 側の RPC コマンド数 | 14 件で停止、以後増えない |
| 経過 | 覚醒確認済みで 4.4 分、初回試行では 9 分 (ただし初回は環境要因で無効) |

**まだ切り分けられていないこと**: **hang / 極端な同期遅延 / 特定 op・graph 構成**のどれか。
上の観測はどれもこの 3 つを区別しない。切り分けるには `graph_compute` の
**進行位置**を出す必要がある (encode 中 / submit 後 / 完了待ち / 特定 op)。

⚠️ **この結果を製品 blocker と断定してはいけない。** 測定機は統合GPU 1 台であり、
discrete GPU 機では挙動が変わりうる。**まず discrete GPU 機 1 台の 2 タブで
L2 (granite MoE / WebGPU peer) を再測定すること** — `harness/runtime-only` の transport は
same-origin BroadcastChannel なので**物理2PC にはできず、その必要もない**
(知りたいのは GPU の差)。⚠️ **実行前に、WebGPU が本当に意図した discrete GPU adapter を
選んだか**を `requestAdapter().info` と peer ログの `adapter_info:` で確認すること。
ノート PC では Chrome が iGPU adapter を選ぶことがあり、その run は無効。

### スコープ外として残したもの

- **upstream `a95a11e5b` (#22464)「Improve performance of mat-vec and mat-mat for MUL_MAT_ID」を
  取っていない。** 今回は性能改善を行わない方針のため。ただし上記の単体性能 (5 GFLOPS) は
  明らかに最適化前の値なので、**次フェーズの第一候補**になる。⚠️ ただし **O11 に効くかは未判定** —
  先に進行位置を特定すること。**効くと仮定して先に入れない**
- **RPC の fail-fast / observability patch (計画の Phase 6) は実装していない。** 計画上も
  「Qwen3.6 必須ではない observability」に分類していた。今回 O11 の切り分けで
  `graph_compute` の内側が見えないことは実際に困ったが、当初設計した内容
  (未対応 op の名前を出す) では O11 には効かない — **未対応 op は存在しないから**。
  必要なのは「どのノードまで実行したか」を出す別の仕掛けであり、設計しなおしになる
- **Qwen3.6 実 GGUF (12.93GB) はダウンロードしていない。** O11 が解けるまで、
  この機で落としても測れるのは load までで、しかも iGPU では M5 が実機と乖離する

## 付録: モデル選定の再現手順

```bash
node scripts/probe-gguf-header.mjs \
  https://huggingface.co/mradermacher/Qwen3.6-35B-A3B-GGUF/resolve/main/Qwen3.6-35B-A3B.Q2_K.gguf
```

期待される出力の要点:

```text
general.architecture : qwen35moe
tokenizer.ggml.pre   : qwen35
qwen35moe.block_count                        40
expert types     : Q3_K, Q2_K
expert bias      : none -> GGML_OP_ADD_ID not needed
nextn tensors    : none
MUL_MAT types unsupported     : none
MUL_MAT_ID types unsupported  : none
```

⚠️ **`nextn tensors : none` と `MUL_MAT_ID types unsupported : none` の両方を満たす版を選ぶこと。**
bartowski 版は MTP を含み `block_count=41` になるため pin では load できない。
unsloth の UD 系は expert が IQ 量子化のため WebGPU peer で実行できない。
